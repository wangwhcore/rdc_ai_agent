# 占位载荷能否省略 —— 实测方案（第 7 步）

> 前置：`docs/meta-model-audit.md`（元模型反推）、`docs/action-wiring-convergence.md`（动作编排收敛）
> 复现命令：`npm run analyze:placeholder`
> 状态：**方案已定，产物零改动**。本文只回答「能不能省、怎么验证」，不做任何落盘。

---

## 0. 结论摘要

第 7 步原本的措辞是「省略 `componentTypeName` / `actionConfig` / `outside` 三个占位载荷」。
实测下来，**这个清单是错的** —— 三个字段的判定各不相同，实际只剩 **1 个**值得动：

| 字段 | 原定 | 实测判定 | 关键依据 |
|---|---|---|---|
| `componentTypeName` | 省略 | ✅ **可省** | 53 份产物「同文件 + 同组件类型」内混用；生成器自身 9 个 Hook 从未输出过它 |
| `actionConfig` | 省略 | ❌ **不可省，剔除清单** | 401 份产物中「同文件 + 同类型混用」**0 份**；且值域含 1 条真实配置 |
| `outside` | 省略 | ⚪ **可选但不在范围** | 63 份混用已证可选；但生成器**压根不产生它** |

> **最重要的结论不是「哪个能省」，而是「清单本身要修正」。**
> 原清单把三个字段归为一类（都叫「占位载荷」），实测证明它们**成因完全不同**：
> 一个是历史样板、一个是带兜底默认值的真实字段、一个根本不由生成器产生。
> 归为一类就会一起动，而一起动必然误伤 `actionConfig`。

---

## 1. 方法论：三层递进判据

这一节比结论更重要 —— 第 7 步的判据是**可复用的**，将来任何一个「这字段能不能省」的问题都用同一套。

### 第一层 · 算分母（绝对次数没有意义）

「`componentTypeName` 出现 11216 次」这句话**回答不了**「能不能省」。
能回答的是分母：「注册表内 N 个 `property`，其中 M 个有它」。

| 字段 | 出现次数 | 真实宿主 | 分母 | 有 | 无 | 省略率 |
|---|---|---|---|---|---|---|
| `componentTypeName` | 11216 | `node.property` | 9451 | 7203 | 2248 | **23.8%** |
| `actionConfig` | 2528 | `node.property` | 9451 | 2059 | 7392 | 78.2% |
| `outside` | 630 | 发布条目 | 6374 | 630 | 5744 | **90.1%** |

> ⚠️ **本步骤踩过的坑（必须记住）**：第一版把「含 `property` 键的对象」当成宿主，
> 统计出 22124 个"组件对象"，然后去数它们有没有 `componentTypeName` —— 结果是 **0 个有**，
> 得出「100% 省略」的荒谬结论。
> **真实宿主是 `node.property` 本身，不是持有 property 的那个组件对象。**
> 「问错对象」在第一层就会把结论整个带偏，且看起来煞有介事。

### 第二层 · 逐文件「有 / 无 / 混用」（排除版本差异）

第一层有个致命漏洞：如果某字段「要么全有、要么全无」，那**很可能是设计器版本差异**
—— 老版本不写、新版本才写。这种情况**不能证明字段可选**。

| 字段 | 全有文件 | 全无文件 | 混用文件 |
|---|---|---|---|
| `componentTypeName` | 237 | 77 | **87** |
| `actionConfig` | 0 | 7 | **394** |
| `outside` | 0 | 299 | **100** |

看起来三个都"混用"了？**别急 —— 这一层会被污染。**

### 第三层 · 同文件 + 同类型 混用（最硬判据）

第二层的 `actionConfig` 显示"混用 394 份"，但这**不能证明可选**。
原因：`actionConfig` 只出现在 `ButtonHook` 上（2053/2053 全有），而 `ColumnHook` / `TextHook`
等 46 种类型**一个都没有**。同一份文件里既有 Button 又有 Column，自然就"混用"了 ——
**那只说明「不同组件类型的字段集本就不同」。**

真正的判据必须收窄到：**同一文件、同一组件类型、至少 2 个实例**内两种写法并存。
这排除了跨类型差异，也排除了版本差异（同一页面不可能跨版本）。

| 字段 | 混用文件 | 一致文件 | 判定 |
|---|---|---|---|
| `componentTypeName` | **53** | 348 | ★ 字段可选，已实证 |
| `actionConfig` | **0** | 401 | 无同类内混用先例 → 省略 = 未走过的路径 |
| `outside` | **63** | 336 | ★ 字段可选，已实证（按同一 `event` 形态比） |

## 2. 逐字段实测明细

### 2.1 `componentTypeName` —— ✅ 可省

**位置**：`$.desktop.components.<ID>.property` 内（**不是**组件对象上）

**值域**：11216 次出现，**100% 是空串**（无一个非空值）

**同类混用**：按组件 `type` 分组，**每一种类型都存在省略实例**

| type | total | 有 | 无 |
|---|---|---|---|
| ButtonHook | 2053 | 1597 | 456 |
| ColumnHook | 2045 | 1621 | 424 |
| TextHook | 1321 | 977 | 344 |
| EditTableColumnHook | 969 | 517 | 452 |
| CardHook | 473 | 431 | 42 |
| SelectHook | 372 | 311 | 61 |

**★ 最强证据 —— 生成器自己就不一致**：

```
写 componentTypeName: '' 的：22 个 Hook
不写（从未输出）的：       9 个 Hook
  ButtonHook / CardHook / DropdownButtonHook / EditTableColumnHook /
  EditTableHook / ImageHook / NeuTransfer / ReUpload / TableHook
```

这 9 个组件（含表格、按钮、卡片、图片、上传 —— 都是高频组件）的产物里**从来没有这个键**，
它们在生产环境正常跑。而另外 22 个 Hook 里的写法是**逐个复制粘贴**的样板：

```js
// 22 个文件里各写一遍，缩进还不统一
componentTypeName: '',
// GridFieldTable.js 里则是塞进一个常量对象
const REGISTERED_COLUMN_DEFAULTS = { align: 'left', componentTypeName: '', ... };
```

**其他层的态度**：

| 层 | 态度 |
|---|---|
| `schema.generated.json` | 记为**可选键**（不在 required 列表） |
| `check/rules/` | **无任何规则**引用它 |
| `ir/lift.js` · `emit.js` | **完全不处理**（纯透传 payload） |

→ **判定：可省。两类独立证据互相印证**（语料 53 份同类混用 + 生成器自身 9 个先例）。

---

### 2.2 `actionConfig` —— ❌ 不可省（从清单剔除）

**位置**：同样在 `property` 内

**值域**：2528 次出现

| 值 | 次数 | 说明 |
|---|---|---|
| `{"enabled":false}` | **2527** | 恒定值 |
| `{"metaId":"...","pageInfo":{},"moduleId":"...",...}` | **1** | **真实动作配置** |

**这是双语义字段**：默认开关 vs 真实配置。
所以「一律删掉 `actionConfig` 键」会**丢那 1 条真实配置** —— 它是语义，不是占位。

**同类混用：0 份 / 401 份全部一致** —— 从未有过省略先例。

**成因**（`builder/components/ButtonHook.js`）：

```js
this.actionConfig = options.actionConfig || { enabled: false };   // :17 兜底默认值
...
actionConfig: this.actionConfig,                                   // :81 输出
```

`|| { enabled: false }` 这一行**恰好解释了为什么 ButtonHook 100% 都有、其他类型 0**：
这是 Button 专属字段，生成器主动兜底，平台设计器也总是输出它。

→ **判定：不可省。** 无先例，且语义非纯占位。
**如果将来要动，只能「按值省」**（省 `{enabled:false}`、留真实配置），但仍然缺先例，不建议。

---

### 2.3 `outside` —— ⚪ 可选，但不在生成器范围

**位置**：发布条目（`pubs` / `successPubs` / `errorPubs` 的元素）

**值域**：630 次（**true 557 / false 73**），省略 5744 条（90.1%）

**同类混用：63 份**（按同一 `event` 形态比）

| event 形态 | 带 outside | 不带 |
|---|---|---|
| `""` 空串 | 96 | 3015 |
| `<ID>.<事件名>` | 328 | 1310 |
| `@@message.success` | 64 | 509 |
| `@@message.error` | 68 | 326 |
| `@@form.init` | **1** | **178** |

`@@form.init` 那 1 vs 178 是干净的铁证：同一文件、同一事件形态，一条显式写了 `outside`、
178 条没写，都上线了。

**但它不在第 7 步范围内** —— 因为 **`grep -rn "outside" builder/` 结果是 0**：
**生成器从来不产生这个字段**。它只存在于平台设计器产出的产物里。
所以「省略 outside」是历史产物 / 导入产物的问题，不是生成器侧能改的。

→ **判定：可选已被实证，但移出第 7 步范围。**

---

## 3. 范围修正（第 7 步的净结论）

```
原定：省略 3 个占位载荷
实际：
  ├── 可做且该做   ：componentTypeName        （1 个）
  ├── 剔除         ：actionConfig             （不可省，语义字段）
  └── 移出范围     ：outside                  （生成器不产生）
```

**第 7 步从「3 个字段」缩到「1 个字段」。**

---

## 4. 收益（说实话：很小）

| 指标 | 数值 |
|---|---|
| 语料侧 | 11216 × 24 字节 ≈ **263 KB** / 23.8 MB = **1.1%** |
| 生成产物 | `inquiry-list-generated.json` 25 处 ≈ 600 字节 / 44633 字节 = **1.3%** |

**所以动机不是性能。** 省掉它买到的是**契约清晰度**：
一个「合同上写了、但永远填空白」的字段，每次读产物都要花成本判断它有没有意义
（是不是漏填了？是不是有我没见过的取值？）。省掉之后，「必填 / 可选 / 占位」的边界才分得清。

**如果收益必须用体积衡量，那这件事不值得做。** 这是取舍的诚实前提。

## 5. 落地顺序（关键：实测在前，改码在后）

### 阶段 1 · 产物级实测（**不改任何代码**）

最小代价的验证方式**不是**改生成器再重新生成，而是**直接改一份产物的 JSON**：

```bash
cd generator
cp ../generated/inquiry-list-generated.json /tmp/exp-A.json          # 对照组（含字段）
# 去掉所有 "componentTypeName": "", 得到实验组
```

这样**零代码改动**就能拿到"省略版产物"。理由：如果实测失败，什么都没改；如果成功，再动代码。

**为什么必须跑起来验证**：省掉字段 = 把 `""` 变成 `undefined`。

| 运行时代码形态 | 省略的后果 |
|---|---|
| `if (p.componentTypeName) {...}` | `""` 与 `undefined` 都是 falsy → **等价，安全** |
| `p.componentTypeName.trim()` / `.length` | **`undefined.trim()` → TypeError** |
| `JSON.stringify(p)` | 输出少一个键（期望内） |

**语料无法区分前两种** —— 这是唯一必须跑起来才知道的事。

### 阶段 2 · 落码（实测通过后）

删掉 22 个文件里的 24 处硬写（含 `GridFieldTable.js` 的常量对象）。
判据：`npm run check:all` 5-5、生成产物里 `componentTypeName` 计数归零。

**若实测不通过**：退而求其次，把 24 处**收敛到 1 处**公共函数
（照 `PUBLISH_SLOT_TO_FIELD` 的做法），**产物字节完全不变**，只是消灭重复样板。

> 这个「退路」也有价值：它让**将来的回滚变成改一行**。

## 6. 实测 SOP（给人执行）

| # | 步骤 | 观察点 | 安全 | 危险 |
|---|---|---|---|---|
| 1 | 准备 A 组（原产物）/ B 组（删字段版），同一页面 | — | — | — |
| 2 | 在测试环境分别导入 A、B | 导入是否报错 | 成功 | 导入校验拒绝 |
| 3 | 打开两个列表页 | 页面是否渲染 | 正常 | 白屏 / 错误页 |
| 4 | 看浏览器控制台 | 有无新增异常 | 无 | `Cannot read properties of undefined (reading 'trim'\|'length'\|'charAt')` |
| 5 | 展开组件属性面板 | 面板是否正常 | 正常 | 空白 / 报错 |
| 6 | **编辑并保存 B 组页面** | 设计器是否回写 | 不回写 → 该字段在设计器里也无位置 | **自动补回** `componentTypeName: ""` → 说明设计器认为它该有 |
| 7 | 对比保存后 B 组产物与 A 组 | diff 范围 | 仅随机 ID / 时间戳 | 多出 `componentTypeName` |

**第 6、7 步是这套 SOP 里信息量最大的两步**，且成本与前面几步相同 ——
只打开页面能证明「渲染不炸」，但证明不了「编辑器回写时会不会把它补回来」。
后者是**从语料完全推不出**的行为，只能实测。

**判读**：
- 2–5 全安全 → 推进到阶段 2
- 任一危险 → 放弃省略，退到「收敛到 1 处」（产物不变）
- 仅第 6 步出现补回 → **仍然可以省**（新产物省略、设计器保存后补回，是稳定的收敛过程）

## 7. 风险

| 风险 | 等级 | 缓解 |
|---|---|---|
| 运行时对空串做字符串操作，`undefined` 抛 TypeError | 中 | SOP 第 4 步专抓这个 |
| 设计器回写补回字段，造成 diff 噪音 | 低 | SOP 第 6、7 步 |
| 「9 个 Hook 从未输出」的先例其实是潜伏 bug | 低 | 这 9 个含表格/按钮等高频组件，若真有问题早暴露；SOP 可确认 |
| 误伤历史产物 | — | **只影响新生成的产物**，401 份语料不动 |

---

## 8. 与既有两条收敛的关系

| | 动作编排收敛（已完成） | 占位载荷省略（本文） |
|---|---|---|
| 动产物？ | **否**（零字节变化） | **是**（少一个键） |
| 验证方式 | `roundtrip` 401 逐字节一致 | 运行时实测（无静态判据可用） |
| 风险 | 低 | 中 |
| 顺序 | 先做 | 后做（「省字段比改字段危险」） |

这个顺序不是随意定的：**改字段的错误会在门禁上暴露，省字段的错误只在运行时暴露。**
