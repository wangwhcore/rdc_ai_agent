## ID004 孤儿组件判据修复 — commit `7cfbbfe`

**起因**：用户质疑「ID004 只认容器 `components[]` 数组引用，那按钮这类会被 **event 事件**引用的

**实测结论：质疑方向对，但具体路径不是 event。**

### 数字

```

  ButtonHook 占误报 364 个 —— 修复前几乎所有行操作按钮都被报成孤儿
calibrate：建议 3499 → 3129；错误 21 → 23（+2 是真实悬空，非误报）
```

### ★ 三处修法

| # | 缺陷 | 命中 | 修法 |
|---|---|---|---|
| 1 | **`TableHook.rowOperationItem[].id` 未落 REFERENCES 表** | 365 | 补进表（22 条）；实测 367 条 / 100% hex / 命中 365 悬空 2 → `error` |

### ★ 一个反直觉的实测：事件引用全是「自我订阅」

指向孤儿的 **416 次 event 寻址，100% 是组件订阅自己**（`<自己id>.click`），**他人订阅 0 例**。

所以：
- **自我订阅不能算「被引用」** —— 未挂载的按钮留下「有 click handler 却无挂载点」，
  恰恰是它成为编辑残留的证据。若算进去，67 个真孤儿会被静默放过。
- **他人订阅必须算「被引用」** —— 当前 0 例，但判据不完整就是将来的坑。

顺带把孤儿分两类：纯残留 vs「有逻辑却忘了挂载」（提示里带自我订阅条数）。

### ★★ 反例清单：`id` 命名 ≠ 引用（防泛化，比补字段更重要）

审计发现其余所有「未进表却像引用」的组合**命中全部为 0**（目标根本不在 components 里）：

```
multiColsConfig[].id          395   associatedFields[].id  112
tabPanels[].id                 65   tableInfo.id            30
operationSet[].id              11   actionList[].id          7
actionConfig.metaId/moduleId    2
```

它们全是**容器内的局部键**（配置项 / 面板 / 字段 / 内嵌表格）。

**决定性证据**：`TabsHook.tabPanels[].id` 命中 **0**，而**同层的** `tabPanels[].layoutId`
命中 **65** 并已进表 —— 同一个对象里，`id` 是局部标识、`layoutId` 才是引用。

**唯一例外是 `rowOperationItem[].id`** —— 它是宿主表格**按行动态渲染的另一个组件**，
语义等同 `columns[].colId`。**不要因为 id 里是 32 位 hex 就收录。**

### ★ 缺陷形态：注释与实现脱节

`rowOperationItem[].id -> componentId 1440/0` **写在 `referenceSpec.js` 的注释里**，

（看起来"已经考虑过了"）。

**教训：规格表的行数 ≠ 覆盖的字段数。注释里提到的统计数字必须能在表里找到对应条目。**
已为此新增 `npm run audit:refs` 让它每次都能被自动查出来。

### 方法：反向排查 > 逐个猜字段

不要「猜哪个字段可能是引用」。反过来做：遍历所有 property 里**像引用的值**

- 命中 > 0 → 真引用，补进表
- 命中 = 0 全悬空 → 局部标识 / 平台元数据，**不收录**

## 成套页面生成：消除 frontId 循环依赖 — commit `adfc860`

**用户报**：`/api/generate/list` 要 `addEditPageFrontId`，
`/api/generate/addEdit` 又要 `listPageFrontId` ——「这两死循环互相依赖了啊」。

### ★ 根因不是死循环，是建模问题

**`frontId` 是页面的主键（保存时分配的 id），不是生成器的输出。**
必须「先有页面 id、后有引用」，而不是「生成完才知道」。

真正的坑是：生成器在调用方没给时**用 `uuid()` 兜底** —— 兜底值永远和另一端对不上，
产物看起来完全正常，只有运行时按 frontId 查不到布局才抛 `reading 'field'`。

实证：不传 `addEditPageFrontId` → `buildListPage` 抛 `E_LAYOUT_REF`。
说明「必填守门」是对的，**缺的是「按正确顺序拿到 id」的入口**。

### 两条路径（都已实现 + HTTP 实测）

| 路径 | 接口 | 适用 |
|---|---|---|
| [A] 先分配再分别生成 | `POST /api/ids` → 三个 frontId，再带 id 调各单页接口 | 设计器已分配 frontId 的真实项目流程 |
| [B] 一次生成整套 | `POST /api/generate/suite` → `{ ids, layouts: { list, addEdit, modal } }` | 纯 API 自动化；`ids` 回传**必须持久化**（是三份布局的主键） |

### ★ 核心不变量（`test/pageSuite.test.js` 锁死）

```
list.addEditPageFrontId   === addEdit 顶层 frontId
list.confirmModalFrontId  === modal  顶层 frontId
addEdit.listPageFrontId   === list   顶层 frontId
modal 的 ok/closeM 命名空间 === modal  顶层 frontId
```

**为什么必须锁**：三份布局互相引用，少接一根线**在生成期完全不可见** ——
生成成功、单文件 check 也过，只有运行时才崩。属于「错误不可见」类，只能靠不变量守。

### 实现要点

- `services/pageSuite.js`：`buildPageSuite` / `allocateIds`
  - 显式传了非法 frontId → **直接抛 `E_LAYOUT_REF`，不静默兜底**（兜底=死循环来源）
  - 空串按「未提供」处理；三个 id 保证互不重复
  - 弹窗按 `rowOperations` 推导（有 delete 才生成），`withConfirmModal` 可覆盖
  - 放在 `services/` 而非 `index.js`：`configNormalizer` 顶层 `require('../index')`，
    加进 index 会形成循环 require（部分导出 → 解构出 undefined）
- `server.js`：诊断带 `layout` 标名，`summary` 增 `byLayout`
- **未纳入查看页**：列表「查看」行操作当前指向 `addEditPageFrontId`
  （`TableHook.buildOperationItems` 既有行为），拆独立 viewPageFrontId 属另一件事

### ★ 测试踩的坑：不要在 `JSON.stringify` 结果上做正则

`value` 里的双引号会被转义成 `\"`，直接匹配 `id: "xxx"` **一个都匹配不到**，
导致「列表页应有 openM 调用」假失败。改为**逐层取出原始字符串**再匹配。

### 门禁

`npm test` 185 项 ✅（+6）/ `check:all` 5-5 / `roundtrip` 401-401 /
`calibrate` 错误 23 持平 / 产物零改动。

## `options.x || true` 恒真缺陷（commit bc430bd）

用户工作区里一直挂着两个未提交的改动（`ColumnHook.js` / `EditTableColumnHook.js`），
本次定性并修复，顺手全库扫同类写法又抓到一个。

### 判据：布尔参数上的 `|| true` 一定是 bug

`x || true`：传 `false` → `true`、传 `undefined` → `true`、传 `0` → `true`
—— **永远为 true，参数不存在**。
对照 `|| false` 是安全的（`false || false` = false），**所以只扫 `|| true`**。
全库 3 处命中，2 处是新增注释，实际代码 1 处。

### ① ColumnHook / EditTableColumnHook 的 hide

用户把 `options.hide || false` 改成 `|| true`。语料（401 份）实测：
`true 1698 / false 20`（98.8%）。

**反直觉但可解释**：`hide=true` 的列样本是「角色名称」「银行编码」「国家」
这类**正常业务字段** —— 若 hide 是「隐藏此列」，这些生产列表页就全空了。
→ 结论：`hide=true` 是**常态值**，**用户改的方向是对的**，错的是 `||` 吞掉了参数。

修：`options.hide !== undefined ? options.hide : true`（与同文件 `fuzzyQuery` 一致）。

### ② AdvanceQueryHook.queryVisible —— 默认值也写反了

`options.queryVisible || true` 恒为 true，但语料实测 **false 299 / true 145**
→ **默认应为 false（67%）**，旧写法**默认值本身与语料相反**。

**同文件相邻 3 个字段（`searchVisible`/`isMerage`/`visible`）都用的 `!== false`**，
只有这个写成 `|| true` —— 「实现内部不一致」这条证据比语料统计更硬。
修：`options.queryVisible || false`（与相邻 `brifShow` 一致）。
★ 改后产物会变（true → false），已确认 check:all 5-5 / 无测试依赖旧值。

### 未决

`EditTableColumnHook` 在语料里带 `hide` 键的**极少**（909 个中仅 2 个，
且都是 true、无 false）—— 「子表列是否该输出这个键」属另一个问题，
本次只保证默认值与主表列一致 + 参数可覆盖，未擅自改输出结构。
