## 架构讨论：工具链是否补全 compiler + check（10:27）

用户提出参照语言项目结构 `mylang/{parser,compiler,check,test,formatter,language-server,docs,examples}`，询问是否应补全 compiler + check 环节。给出的结论与建议：

- **结论**：要补，但不能照搬真编译器。DSL 与 Layout JSON 语义距离极近（DSL 基本是配置对象的语法糖），做多趟 pass / IR 优化是过渡设计。
- **核心判断**：当前真正的缺口不是 compiler，而是**缺少显式中间表示（Page IR）**。`builder/*` 目前一次性做了解析+组装+发射，`validator.js` 是发射后置校验。
- **建议拆分为三段**：`parser`（DSL→Page IR，纯数据、可序列化可 diff）→ `check`（在 IR 上跑规则，输出 `{severity, path, message}` 带位置诊断）→ `compiler`（IR→Layout JSON，瘦 emit，纯函数）。
- **IR 是杠杆点**：formatter、language-server、往返测试、自然语言入口都从 IR 派生；无 IR 则各自重复实现解析。
- **check 是命门**：目标运行时引擎（neusoft_web / front_web）不归自己控制，`CardHook.layoutId`/`toolContainerId`/`TableHook.columns.colId`/`rowOperationItem.id`/`AdvanceQueryHook.associateId` 断引用时引擎**静默渲染空白不报错**。需从现有 5 条规则扩到约 30 条（引用完整性、组件 property 白名单、dataSource 契约、ID 唯一性、layoutList↔components 双向一致）。
- **不做**：手写词法/语法分析器、类型推导、多趟 pass、目标平台适配层。
- **建议顺序**：① 抽 Page IR（builder 内部改 AST→IR→JSON，对外行为不变，测试保持全绿）→ ② check 扩到 30 条，用 `parsed-dsl` 401 个脚本当回归语料 → ③ NL→IR→check→JSON 收编自然语言入口，check 兼做 LLM 输出守门员 → ④ 最后做 formatter 与幂等往返测试。
- **额外发现**：`parsed-dsl` 401 个已有脚本可直接作为 `JSON→IR→DSL→IR→JSON` 幂等往返测试的现成用例集，是成本最低收益最高的动作。
- **暂缓项**：目录结构重构（8 目录仪式感）暂不建议，扁平结构先不动，优先做 IR 抽取 + check 扩容。

## 定位并修复「运行时 TypeError: reading 'field'」根因（11:40）

### 根因定位
从不被我们控制的运行时里只能看到一行报错，于是用**语料实证**反推契约：

1. 该报错来自运行时布局分发器 `RenderLayout(e) { var t = e ? e.layoutInfo.field : void 0; ... }`

2. 语料中 `layoutInfo` **只出现在 `$.desktop` / `$.pad` / `$.phone` 三处**（401 份全量扫描），
   且 `pad`/`phone` 有 398 份是空对象 `{}` —— 说明不是无脑遍历设备，而是**按引用查布局失败后拿到空节点**。

| 引用字段 | 命名空间 | 命中 |

| `layoutInfo.componentIds[]` | regionId 或预设槽位名 | 837 + 203（如 `BottomLeft`） |

## JSON 格式检查与强制修订（承接高级查询 + style/validate 回归之后）

需求原话：「由于生成的 json 格式不正确导致的错误很没有必要，加入一个 json 格式检查与强制修订吧？」

### 选型
用开源库 **`jsonrepair`**（josdejong/jsonrepair，MIT，v3.15.0，CJS 可 `require`）。
选它是因为它一次覆盖尾随逗号 / 单引号 / 注释 / 未引号键 / 键缺值 / 截断，
比自写宽容解析器可靠得多。定位为**可选依赖**：`require` 包在 try/catch 里，
缺失时自动降级到内置手段，不破坏任何既有能力。

### 新增模块
| 文件 | 职责 |
|---|---|
| `ir/jsonFormat.js` | 文本层：`inspectText` / `repairText` / `diagnose`；缺陷词表 12 种；状态机 scanner 同时产出 defects 与可编辑 spans |
| `ir/jsonGate.js` | 门禁：`enforce(input)`（对象或文件文本）→ 格式检查 → 强制修订 → 门 A 结构不变量 → 门 B check 零 error |
| `check/rules/format.js` | 规则组 `JSON001`（value 是对象）/ `JSON003`（键名重复）/ `JSON002`（值层解出非对象，放 engine）/ `INPUT003` 增强 |
| `test/jsonFormat.test.js` | 缺陷分类、内容保真、语义告警、拒绝场景、401 语料零误报 |

修订手段按安全性排序：`strip-bom` → `escape-control` → **`jsonrepair`** →
`normalize-loose`（内置兜底）→ `closer-patch`（最后手段）。

### 三个通过测试才挖出来的关键决策
1. **「看不出 JSON 结构」的文本必须直接拒绝**，不能交给 jsonrepair：
   实测它会把 `'这不是 JSON'` 揉成 `'"这不是 JSON"'`、`'<<<<'` 揉成合法 JSON。
   加 `looksLikeJson()` 闸门（首个非空白字符须属 `{ [ " - 数字 t/f/n`）。
2. **`truncated` 虽 fatal 但可修**：判定「缺陷是否解释了 parse 失败」时
   不能用 `fatal` 标记，要用 **`fix` 字段是否存在** —— 否则 `Unexpected end of
   JSON input` 会被误判成不可修（这是第一版实测出来的 bug）。
3. **`INPUT003` / `JSON002` 必须放 engine 提前返回，不能放规则组**：
   值层不可解析时拿不到 IR，规则组跑不起来。这是结构约束。

### 幂等与告警约定
- `JSON.parse` 已通过但只有语义类缺陷（键名重复）时，`repairText` 返回
  `ok:true, method:null` → `diagnose` 据此判 `repairable:false`（「能解析 ≠ 没问题」）。
- `undefined→null`、`{"a":}` 补 `null`、靠 `closer-patch` 可解析 → 必须进 `warnings`。
- 键名重复**只报不改**（自动修等于替人做语义取舍）。

## 结论性判断：低代码 DSL 演进的路线取舍（重要，后续会反复用到）

用户的外部 AI 提议「先定义 16 个并列 DSL（Page/List/Form/Detail/Component/DataSource/
Data/Context/Event/Condition/Action/Flow/Permission/Page Dependency/Extension/JSON Schema），
再拿供应商信息做案例」。**评估结论：方向对，颗粒度错，顺序反了。**

- **不正交**：List/Form/Detail 是同一 `View` 的 `kind`；Page Dependency 是 `View` 字段；
  Context 是 Binding 的 `params`；Permission 是横切 `guard`。并列化会导致同一件事有多种
  合法写法 —— 这正是打补丁痛苦的根源。
- **元模型已存在且是数据驱动的**：`ir/lift.js` 的 `PAGE_KINDS`（7 种 kind 一个模型）、
  `lift`/`emit` 双向无损（401 份逐字节一致）、`ir/schema.generated.json`
  （**从 401 份语料统计**，18KB）、`check/` 8 组 58 条规则、`ir/jsonFormat.js`+`jsonGate.js`。
  凭想象设计的 16 DSL 不该覆盖这套。
- **真实痛点不是「表达力不足」**：格式错误、CSSStyleDeclaration 崩溃、frontId 漂移、
  tagStyle/singleValidate/allowEmpty 回归、401 存量无回归基线 —— 五个全是
  **生成器 ↔ 运行时契约不稳**。契约不稳时引入新 DSL = 拆地基修墙皮。
- **建议收敛为 4 概念**：`View` / `Resource` / `Behavior` / `Binding`，
  `Permission` 降级为 guard 属性，`Extension` 延后 V2（门槛：同一需求在逃生舱出现 ≥2 次），
  JSON Schema **只留 1 份**（4 概念 + `$defs` 复用），不做 16 份 Schema / 16 个 validator。
- **顺序应该是「先验证，后设计」**：
  ① 用 401 份语料反推元模型，统计「同一语义有 N 种写法」（收敛项）与
  「根本表达不了」（新增候选）—— 新增概念数量由统计决定，不由想象力决定；
  ② 把 8 个 `/api/generate/*` 端点收敛为 1 个 `POST /api/generate`（body 里
  `{ view: { kind } }`）—— 不需要新 DSL、纯 API 整形、风险极低；
  ③ 选一个**新页面**跑通 元模型→生成→运行时→上线 闭环（不能改存量）；
  ④ 只补第 ① 步统计出的真实缺口。
- **`/api/generate/list`「最终请求结构」这个动作本身是错的**：当前已有 8 个
  `/api/generate/*` 端点，一类页面一个端点，这是在固化反模式。
- **采购订单例子**：Event→Action 拆解对，但真正难点是
  **`openPage({ params, onReturn: { refresh, set } })` 的跨页返回回传**，
  不是 Flow DSL。按 ROI：`onReturn` 回传 > 字段联动（现有 `datasource`+`references`
  大概率已能表达）> 跨页新建成父级并回传新 id。
